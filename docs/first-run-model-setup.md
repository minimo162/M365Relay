# 初回モデル準備（0.2.25候補）

新しく作るM365Relay専用VS Codeプロファイルだけに、初回準備と状態表示を含む小さな初期化用VSIX（拡張版`0.1.1`）を標準CLIでインストールする。専用のvscode-extensionsを指定し、通常のVS Codeの拡張フォルダーを変更しない。既存の正規`0.1.0`専用拡張がある場合は、旧版を不一致として停止せず、新しい版を同じ専用拡張フォルダーへ追加インストールする。

拡張は専用のglobal設定を確認し、一度だけ標準のManage Language Modelsを実行する。モデル登録を確認したらチャットを開いて最大化する。新規プロファイルでは標準の--skip-welcomeで任意のWelcome表示を省き、workbench.editor.useModal=offでモデル管理画面が入力を覆わないようにする。M365へのサインインは引き続き利用者が行う。

初回の試行済み状態はVS CodeのglobalStateへ保存する。失敗した場合も自動反復せず、「M365Relay: 接続モデルを準備」から利用者が明示的に再実行できる。後からCopilotを無効化した状態を再起動だけで戻さない。ワークスペース設定だけでは初期化を有効にできない。

通常CLIでのVSIXインストール、新規プロファイルのモデル登録、M365Relay選択済み・履歴付きチャット最大化を実画面で確認した。以前のモーダル閉鎖案は採用しておらず、内部DBやVS Code本体の直接書換えも行わない。

専用拡張は、起動時に渡された`M365_RELAY_WORKSPACE_STATE`だけへ最後に観測した最初のworkspaceを保存する。通常のVS Code設定・DBは参照せず、次回の引数なし起動では保存されたフォルダーを実在確認してから再利用する。

配布候補のVSIXと同梱ランタイムを使う新規VS Codeプロファイルで、手動のモデル管理・モデル選択なしに最初の依頼を送信。実M365から指定文字列「初回テストOK-719」を受信し、1要求・14,426ms・Relayエラー0を確認した。M365側は既にサインイン済みの専用Edgeを利用しており、新しいアカウントの認証を自動化した試験ではない。配布のBridge.cmd runをもう一度実行しても、同じウィンドウへ復帰し、追加要求は発生しなかった。

Windows配布10検査と173テストを確認。Windows CIで一時パスの8.3表記差を誤判定したテストは、実パス同士の比較へ修正した。企業ポリシーや別のVS Codeバージョンでの検証は別途必要。以前からある専用環境でモデルが表示されない場合は、標準のManage Language Modelsを手動で開く。
