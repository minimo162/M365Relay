# 画像入力搬送の実装と検証

PNG/JPEG data URLを検証し、所属message/part位置とSHA256、固定形式のfileNameを本文参照へ残す。画像bytesは本文から分離し、要求ごとの一時ディレクトリから所有検証済みM365タブのfile inputへ1回だけ設定する。外部URL・任意パス取得はしない。

既存添付があれば停止。添付名・枚数・進捗表示を確認し、テキスト送信直前にも再確認する。画面の送信可能状態も既存処理で確認する。初回確認ダイアログは操作せず利用者に委ねる。画像アップロード自身を外部送信として事前に台帳へ記録するので、結果不明をnot_sentへ戻して再添付しない。

実M365で製品prepareRequest/画像添付/M365Backend/parseEnvelopeを接続した試験は14939ms、画像添付1882ms。識別子、文字、赤枠overflow=trueと緑枠falseが一致。方向はhorizontalと回答し、厳密なright判定の証拠にはしない。

さらに認証付きHTTPサーバー経由で、厳密JSON schemaのidentifier/redOverflow/greenOverflowを完全一致で確認。同一の画像付き要求を再送すると409 duplicate_requestで拒否。試験サーバーは終了し、常駐配布サーバーとは別だった。

1枚4MiB、4枚/合計12MiB、各1600万画素まで。HTTPは画像対応時20MiB以内、本文はエスケープ後120000文字以内。PNGはコンテナーと寸法、JPEGは対応フレームと寸法を検査するが、ここだけで全デコードの安全性を保証するものではない。

CLI実バックエンドと生成モデル設定で画像対応を有効にした。本体135テスト成功。単体では未対応backendによる画像省略拒否、添付欄曖昧時の停止、送信直前変更、台帳記録順、一時ファイル削除を検査。VS Codeの実view_image出力形式、複数画像、実JPEG、会社環境での通し確認は残る。

証拠: .local/vision-probe/integrated-result.json、http-result.json。画像データは実験画像のみ。ログには画像bytesを記録しない。アップロードされたクラウド側コピーの自動削除は実装していない。
