# 自動設定後の実チャットと初回待ち時間

状態：partial。高速で実用的なアプリという全体目標は継続中。

## 実チャット確認

配布ZIP `10141875ba23` のRun.cmdから、同梱NodeでRelayと専用VS Codeを起動した。
ユーザーがフォルダーを信頼済みにしたことを、VS Codeの「You trust this folder」表示でも確認。
初回のモデル選択にAutoしか出ていないときは、Manage Modelsを開くことで登録済みM365Relayが表示された。キーの貼付やJSON手編集は行っていない。
「接続できました」という指定どおりの回答を実M365から受信した。

## 遅延の切り分け

最初の接続確認では、次の要求が同一の直列化されたRelayへ入った。

| 用途 | 文字数 | 結果 |
|---|---:|---|
| 進捗文言の事前生成1 | 7,019 | 約10秒で入力照合失敗、未送信 |
| 進捗文言の事前生成2 | 7,018 | 約10.3秒で応答 |
| 主処理 | 95,179 | 約8.7秒で応答 |

VS Codeログの主処理所要時間は28,790ms。初回のInlineChatProgressMessagesのprewarmが2種類の文言を生成し、主処理を待たせていた。
これはインストール済みVS Code 1.136.1 / Copilot 0.64.1のコードと実ログを照合して確認した。

## 設定変更と比較

専用設定の既定を以下に変更した。

- `chat.byokUtilityModelDefault: none`
- `chat.utilityModel: customendpoint/m365-copilot-ui`

小型補助モデルを自動で主モデルへ割り当てず、進捗文言の事前生成にM365接続を使わない。
通常の補助モデルは明示的にM365Relayへ接続し、別のモデルAPI契約を要求しない。
小型補助モデルに依存する全機能の互換性を証明したわけではなく、編集支援を含む後続の実機確認は必要。
ユーザーがカスタマイズした補助モデル設定は保持する。旧版が生成した単一のmainAgent既定だけの設定は移行する。

VS Codeを再読み込みしてキャッシュを作り直した後、新しいチャットで比較した。依頼は同じ短い接続確認で、重複要求と区別するため「2回目」を付けた。
変更後は主処理1回のみ（95,184文字）、VS Code側で8,721ms、指定どおりの回答となった。
バックエンド本体、M365の生成設定、応答安定待ちは変更していない。主処理自体は変更前も約8.7秒であり、除去できたのは補助要求の待ち時間。

## 制限

- 比較は1組。モデルの一般的な速度向上や統計的な性能保証ではない。
- 初回の片方の補助要求には入力照合失敗が含まれる。単純に一定割合の高速化を保証しない。
- 比較時は配布版1014187のサーバーを動かしたまま、ソースの新setupで専用設定を更新した。旧配布ZIPそのものに新しい既定が含まれるわけではない。
- 大きな作業の往復数、無介入の安定性、入力が空になる症状、会社環境は未解決・未検証。
- VS Codeが表示する小型補助モデルの設定案内は残る。初回導線をさらに分かりやすくする必要がある。
